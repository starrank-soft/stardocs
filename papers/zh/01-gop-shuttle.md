## 摘要

浏览器视频编辑器同时承载播放、跳转、拖动预览、停留精确化和时间线缩略图等交互。它们具有不同的时延、精度和覆盖范围要求，却共享同一批压缩视频、解码器和显存资源。常见实现会为每种交互建立独立任务队列：播放向前解码，seek 从关键帧重新启动，scrub 不断取消旧请求，缩略图再启动另一套后台解码。这样的命令式调度会重复读取与解码同一 GOP 前缀，在模式切换时丢弃仍有价值的在途输出，并让后台工作与当前画面争抢资源。

本文提出一种“班车式解码”模型。系统先把所有交互解析成同一份不可变时序需求，再投影为 `point`、`stream`、`range` 与 `grid` 四类源空间几何需求。纯规划器按来源、样本与随机访问 GOP 合并需求，生成可替换的 GOP Flight 目标；有状态协调器则复用仍然有效的前向解码路线、在途输出和温热检查点。一个 Flight 可以像一辆从关键帧出发、沿解码依赖顺序前进的班车，在多个目标站点交付帧，而不是为每个目标重新叫一辆“出租车”。移动 scrub 可以即时展示误差受限的邻近缓存帧，但精确目标仍保持为未完成的解码义务；缩略图也订阅同一网格站点，而不建立第二套解码系统。

本文不声称发明 GOP、关键帧跳转、缩略图或解码器缓存。贡献在于：用统一需求协调代替模式专属命令队列，并通过可复现实验证明跨交互复用、在途覆盖和精确/近似分离是否降低工作放大、解码器抖动与交互时延。

## 1. 问题：编辑器不是播放器

普通播放器的主要问题是持续向前播放。视频编辑器的游标却会在几种行为之间高频切换：

1. 正向播放，希望每个时钟 tick 都得到所有可见层的精确合成帧；
2. 点击时间线，要求目标位置的精确帧；
3. 快速拖动，希望尽快看到方向一致的视觉反馈；
4. 停止拖动，必须收敛到精确帧；
5. 缩放或滚动时间线，需要均匀、稀疏的缩略图覆盖；
6. 多层合成，同一时刻可能依赖多个独立视频来源；
7. 重复素材，同一来源样本可能同时服务多个 Clip。

如果系统把这些行为分别实现成 `playTask`、`seekTask`、`scrubTask` 和 `thumbnailTask`，交互语义就会一路泄漏到物理解码层。每次模式变化都会被翻译成“取消旧任务、创建新任务”，但压缩视频的实际工作并没有按交互模式划分。多个请求可能落在同一个 GOP，甚至需要同一段前缀。

本文的基本判断是：

> 播放、seek、scrub 和缩略图是不同的需求生成方式，不应该是不同的解码器实现。

## 2. 班车隐喻

### 2.1 出租车模型

命令式 seek 类似于为每个目标单独叫车：

```text
目标帧 A → 找关键帧 → 新建/重置解码器 → 解到 A
目标帧 B → 找关键帧 → 新建/重置解码器 → 解到 B
目标帧 C → 找关键帧 → 新建/重置解码器 → 解到 C
```

当 A、B、C 位于同一长 GOP 内时，三条路线会反复经过同一个前缀。快速 scrub 还会在旧车尚未到站时不断取消订单。

### 2.2 班车模型

GOP Flight 从真实随机访问样本出发，按照依赖顺序向前推进：

```text
关键帧 K ── s1 ── s2 ── A ── s4 ── B ── s6 ── C
                       ↑          ↑          ↑
                    point      thumbnail   prediction
```

规划器先把同一路线上的站点合并，一条物理解码路线可以依次交付 A、B、C。需求改变时，系统替换“要到哪些站”，而不是立刻销毁“正在跑的车”。

这个隐喻有三个边界：

- Flight 不是视频格式里的新概念，而是运行时对一次可复用前向解码路线的命名；
- 不同 GOP 或不同来源通常仍需要不同路线；
- 一辆班车不能无限载客，解码器、在途帧、缓存和读取都有独立预算。

## 3. 一份时序真相

系统在全局时间 (t) 上解析不可变需求快照：

\[
R_t = Resolve(t, motion_t, viewport_t, composition_t)
\]

其中包含：

- `point`：全局时刻 (t) 上所有可见视频与图片层；
- `transport`：交互继续发展时有价值的连续窗口；
- `viewport`：由时间线缩放、刻度和 overscan 产生的均匀网格；
- `frameSelection`：当前允许如何呈现缓存帧的策略。

Clip 边界不是事件。一个点、区间或网格与 Clip 相交后，才通过 Clip 的时间偏移和速度投影到源空间。下游调度器不再知道“这是播放请求”还是“这是 scrub 请求”，只处理源样本几何。

### 3.1 四类解码需求

| 需求 | 含义 |
|---|---|
| `point` | 一个精确 floor-PTS 样本 |
| `stream` | 滚动的连续范围 |
| `range` | 有限稠密区间或显式稀疏目标 |
| `grid` | 从全局时间线刻度投影出的稀疏样本 |

这四类是几何，不是交互模式。未来增加“键盘逐帧”“智能预览”或“局部循环播放”，只要能投影到已有几何，就不需要新增物理解码任务类型。

## 4. 从需求到 Flight

### 4.1 纯规划

源空间需求经过统一 SourceIndex 量化，按 `(source, sample)` 去重，再按随机访问 GOP 分组：

\[
F_t = Plan(Project(R_t), cache_t, pending_t)
\]

一个 Flight 目标是不可变值：

```text
{
  source,
  keySample,
  forwardEnd,
  requiredTargets,
  priority,
  routeReplay
}
```

必须区分三件事：

| 概念 | 责任 |
|---|---|
| Flight Target | 描述这条路线当前需要覆盖的站点 |
| Flight Driver | 持续读取最新 Target 并推进路线 |
| Decoder Session | 真实的 VideoDecoder、游标、参考帧与在途输出 |

把三者合并成一个“解码任务”，就无法在目标变化时保留仍有价值的物理状态。

### 4.2 协调而不是取消

运行态只在一个边界做有状态协调：

\[
Live_{t+1} = Reconcile(Live_t, F_{t+1})
\]

一个站点从最新目标中消失后，Driver 在下一次提交守卫处停止继续喂样本；已经发出的读取和解码输出仍然可以完成，只要它们对最新需求有价值。只有来源失效或运行时销毁才需要硬中止。

### 4.3 在途输出也是覆盖

“已经给解码器喂过输入”不等于帧一定会到达。reset、解码错误和资源回收都可能让输出消失。因此系统用 output ticket 表示在途覆盖：

- ticket 命中最新目标时，不允许启动重复路线；
- reset 或 reconfigure 之前，先判断在途输出是否仍能满足最新需求；
- 只有输出落入缓存后，才成为物化覆盖。

【证据缺口 G-E1】每个样本必须拥有从读取、提交、输出、入缓存、呈现、丢弃到 close 的完整 trace，不能靠 elapsed time 推测在途状态。

## 5. 精确解码与近似呈现分离

移动 scrub 的目标是快速反馈，不是立即证明精确完成。系统可以在运动时呈现邻近缓存样本：

\[
\hat{s}_t = argmin_{s \in Cache}|s-s_t|
\]

但必须满足：

- 误差不超过由速度、加速度和 viewport 刻度决定的界限；
- 方向稳定时，呈现样本保持单调；
- 慢速拖动只允许目标两侧极近样本；
- 精确目标 (s_t) 始终保留为未完成需求；
- 停留、committed seek 和播放不接受近似完成。

这解决了一个常见语义错误：UI 看到了“差不多的帧”，调度器就误以为请求已经完成。GOPFlight 明确区分“现在有像素可看”和“精确义务已满足”。

## 6. 缩略图不是第二个解码器

时间线缩略图由全局刻度产生 `grid` 站点。它们与前台 point、stream 和 range 一起进入 Flight 规划：

- grid 可以自己启动低优先级 Flight；
- 前台 Flight 正好经过目标样本时，可以直接交付；
- 同一来源样本可以服务多个 Clip 和多个缩略图订阅者；
- 邻近帧可以临时提供视觉占位，但不能永久满足精确网格站点。

已有研究早已证明低清预览和缩略图网格有助于 scrub。Swift 使用低分辨率视频降低在线拖动时延，Swifter 使用预缓存网格辅助长视频定位，Spread Loading 用粗到细的加载顺序尽早覆盖全局。本文的新增点不是“显示缩略图”，而是缩略图与前台交互共享同一物理解码成果。

## 7. 资源预算与公平性

必须分别限制：

- VideoDecoder 驻留数量；
- 同时运行的 Flight Driver 数量；
- 解码帧字节；
- 在途输出字节；
- 压缩 GOP 缓存；
- I/O 并发；
- 推测样本数量。

不能因为允许六个温热解码器，就推导出可以缓存六倍 GPU 帧；也不能因为 transport 窗口有 1.5 秒，就立即把全部窗口解完。

当前策略让当前合成帧高于 transport，transport 高于 grid。相同优先级路线按样本数或字节 quantum 轮转。每个当前可见来源至少获得一个强制样本，剩余预算才用于前向深度和未来 Clip 广度。

【研发观察 G-W1】每次策略修改必须同时记录可见反馈、精确率、提交样本、输出字节、reset 次数、最大饥饿和峰值驻留；单看 FPS 会掩盖工作放大。

## 8. 与既有工作的关系

- WebCodecs 提供低层解码机制，但不定义编辑器的交互调度策略。
- GOP 随机访问、关键帧 seek、缓存与预取都有成熟研究，不能作为本文独占贡献。
- Swift、Swifter、HiStory 和 Spread Loading 研究的是导航交互与预览交付。
- Vega-Video 把视频纳入声明式可视化语法，并对连续 scrub 做编码感知优化，是最接近的近期工作之一。

【创新边界 G-N1】论文应使用“统一需求协调和路线复用”，不要使用“新解码算法”或“首次 GOP 调度”。

## 9. 实验设计

### 9.1 基线

1. 原生 HTMLMediaElement；
2. 无状态 WebCodecs：每个请求从关键帧重新开始；
3. 按模式分离的 play/seek/scrub/thumbnail 队列；
4. 统一需求但不按 GOP 合并；
5. 合并 Flight 但不把 pending output 视为覆盖；
6. 完整规划但无温热 checkpoint；
7. 完整 GOPFlight；
8. 预生成 sprite sheet，作为缩略图专用基线。

### 9.2 工作负载

- H.264、VP9、AV1，以及可用环境中的 HEVC；
- 长/短 GOP、open/closed GOP、含/不含 B-frame；
- CFR/VFR、720p/1080p/1440p/4K；
- 1/3/6 个同时可见层；
- 单一长 Clip、大量短 Clip、重复引用同一来源；
- 连续播放、随机 seek、慢速 scrub、快速 scrub、反复掉头、scrub 后停留、scrub 后立即播放；
- 冷缓存与热缓存、本地与远程来源。

### 9.3 指标

- 播放启动时延与精确合成率；
- seek 到精确帧时延；
- scrub 可见反馈率、最大反馈间隔、时间误差和单调性；
- dwell 到精确帧时延；
- 缩略图首次覆盖和完整覆盖时延；
- 提交、输出、缓存、呈现与丢弃样本数；
- GOP 前缀重放、重复提交、configure/reset/close 次数；
- 解码帧、pending output、缩略图与压缩缓存峰值字节；
- 多层来源公平性与最大饥饿。

【实验任务 G-X1】所有 WebCodecs 基线必须共享同一 demux、SourceIndex、缓存、合成器和呈现规则，只替换被研究的调度机制。

【实验任务 G-X2】把现有性能历史改造成冻结 commit 的 baseline/treatment 实验；历史 revision 对比不能替代受控消融。

## 10. 当前先导数据

现有单机 trace 可用于选指标，但不能直接写成最终结论：

- 三层播放的历史策略精确合成为 `123/135（91.1%）`；两次当前策略记录为 `150/153（98.0%）` 与 `158/162（97.5%）`；
- staged play admission 两次为 `314 ms` 与 `309 ms`，启动后第一秒未出现饥饿；
- 冷缩略图/grid 的可见反馈为 `27.4%–30.5%`，最大饥饿 `192–218 ms`；
- 128 张缩略图完成后的反馈为 `46.7%–49.1%`，最大饥饿 `59–71 ms`。

【证据缺口 G-E2】这些数据来自开发过程，改动并非单变量，设备与素材范围有限。最终论文必须重跑受控实验并保存原始 trace、浏览器版本、硬件、素材 manifest 和分析脚本。

## 11. 面向工程读者的文章稿

视频编辑器里的解码器，经常被我们写成一支出租车队。用户点一下时间线，我们叫一辆车；拖一下游标，再叫一辆；方向反转，取消前一辆；时间线需要缩略图，后台车队再出发。每个请求看起来都独立、清楚、容易实现，但压缩视频并不按这些 UI 动作组织。

压缩视频更像一条有固定起点和行驶方向的线路。想拿到 GOP 中间的一帧，通常要从更早的随机访问点开始，按依赖顺序经过前面的帧。如果三个目标都在同一条线路上，为它们分别启动三次解码，就是让三辆出租车重复走同一段路。

班车式解码换了一个问题：系统不再问“现在要执行哪个 seek 命令”，而是问“当前有哪些站必须到达，哪些路线已经在跑，哪些在途乘客仍然有价值”。播放、seek、scrub 和缩略图只负责描述站点，GOP Flight 负责把站点合并成路线。

这也改变了取消的含义。游标离开一个位置，不代表所有旧工作都必须被销毁。已经提交给解码器、即将输出的帧，可能恰好命中新的位置或缩略图站点。真正合理的动作是拿最新需求重新协调，而不是把每次交互变化都翻译成 reset。

另一个关键点是把“看到了画面”和“完成了精确解码”分开。快速拖动时，附近缓存帧足以给用户方向感；但游标停下后，编辑器必须给出精确帧。近似呈现是一项 UI 策略，不能偷偷改变解码器的完成条件。

最终，GOPFlight 不是一种新 codec，也不是一句“多做缓存”。它是一种调度建模方式：让不断变化的编辑意图成为可替换的需求值，让真实解码路线跨需求更新继续存在。班车比出租车高效，不是因为它跑得更快，而是因为它避免为每位乘客重复走同一条路。
