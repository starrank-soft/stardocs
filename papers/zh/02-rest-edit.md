## 摘要

当视频工程、图形工程或其他创作工程已经被建模为稳定的结构化运行态时，让大语言模型重新输出完整文档并覆盖原状态，会放大模型输出长度、覆盖并发修改、破坏稳定标识，并使局部错误影响整个工程。现有的通用结构化差分格式能够表达局部变更，但其路径、载荷和流式完成条件并不一定适合语言模型逐 token 生成。

本文提出 REST-Edit，一种受 REST 资源操作方式启发、但不等同于 HTTP REST 或 JSON Patch 的轻量级编辑协议。协议使用短稳定标识 `#id` 指向已经建模的语义节点，以 `PATCH`、`POST`、`PUT` 和 `DELETE` 表达属性修改、子节点创建、节点移动和节点删除，并允许原生领域标记语言作为创建载荷。它的主要设计目标不是发明四个操作名称，而是让局部编辑同时满足四项条件：语义定位短、逐行可判定、可随模型输出渐进解析、可在提交态输入到达后安全收口。

我们进一步给出一种“实时前缀 + 提交围栏”的执行机制：连续的实时输入前缀可以立即产生经过模式验证的局部修改；若实时通道出现缺口，执行器保留已验证前缀、停止消费错位后缀，并由最终提交输入补齐缺失部分。完整调用只产生一次权威结果，并归并为一个 Undo 边界。本文计划从任务成功率、首个可见修改延迟、输入/输出 token、传输字节、解析恢复、误修改范围和协同压力等方面，与完整文档重写、JSON Patch、函数参数式多工具调用及非流式编辑脚本进行比较。

## 1. 研究问题

本文研究的不是“如何修改 JSON”这一通用问题，而是更具体的问题：

> 当一个创作工程已经在运行态中形成稳定抽象，怎样给生成式 AI 一种足够短、足够语义化、能够流式解析且不会要求模型重建整个工程的精确编辑接口？

这个问题包含三个不同层面：

1. **表示层**：模型如何简短地指出“改哪个语义对象的哪个方面”；
2. **增量层**：模型尚未输出完整参数时，系统能否确定已经完成的局部操作；
3. **执行层**：实时增量可能丢失、重连或重复时，如何与最终提交输入收敛到同一结果。

## 2. 为什么完整覆盖不适合运行态工程

完整文档生成在“从零创建”时很自然，但在“修改现有工程”时会产生结构性问题。

### 2.1 运行态已经完成建模

视频时间线并不是一段任意 JSON。节点具有稳定 ID、父子约束、引用关系、顺序语义、模式约束和协同历史。把完整序列化文本重新交给模型生成，相当于要求模型重复完成一次系统已经完成的建模。

### 2.2 局部意图被放大为全局写入

用户可能只要求把一个片段的不透明度从 `1` 改为 `0.8`。完整覆盖却要求模型复述工程中的其他轨道、片段、素材引用和参数。任何遗漏或幻觉都会把局部意图扩散成全局风险。

### 2.3 覆盖范围与协同冲突范围同步扩大

协同并不是 REST-Edit 独有的能力，JSON Patch、CRDT 和事务系统都可以支持协同与 Undo。这里更准确的论点是：**局部协议缩小了单次意图的写集合**。当用户和 AI 同时编辑不同节点时，更小的写集合更容易保留彼此的工作；最终如何合并，仍由底层 CRDT 或事务系统负责。

### 2.4 输出成本与工程大小耦合

完整重写的输出量近似随工程规模增长；语义局部编辑的输出量主要随变更规模增长。如果工程有 (N) 个序列化单元，而一次操作只修改 (k) 个单元，理想局部协议的输出复杂度接近 (O(k))，完整覆盖则接近 (O(N))。这不是实际 token 节省率的结论，实际比例必须通过真实任务测量。

> **[待补 R-D1：真实项目规模分布]** 记录 VML 节点数、完整序列化 token、单次用户意图涉及节点数与局部脚本 token。

## 3. 协议设计

### 3.1 有限的 REST-like 类比

REST-Edit 使用“资源 + 操作”的直觉：稳定节点是资源，操作名称表达对资源的意图。但本文不会声称它实现了 REST 架构风格，因为它不是一套 HTTP 网络资源架构，也不讨论缓存、统一接口的全部约束或超媒体状态转移。

因此，准确表述是：

- 协议是 **REST-inspired** 或 **RESTful-like**；
- 核心是面向语义资源的局部编辑；
- 四个操作名称是可理解的表面形式，不是主要创新本身。

### 3.2 短稳定标识

```text
PATCH #clip_42
opacity="0.8"
```

`#clip_42` 直接定位运行态中的稳定节点。协议不要求模型生成类似 `/compositions/0/tracks/3/clips/12/opacity` 的长结构路径。

短 ID 有三项作用：

1. 避免把容器布局、数组下标和领域意图混在同一地址中；
2. 节点重排后，地址仍然稳定；
3. 模型可以从上下文、读取工具或创建结果中复用 ID。

短并不等于模糊。ID 必须在所选文件内唯一，执行器必须拒绝不存在、跨文件或不允许访问的目标。

### 3.3 四种语义操作

#### PATCH：修改节点属性或文本数据

```text
PATCH #clip_42
start="1000000"
duration="3000000"
opacity="0.8"
```

每个完整属性行可以独立解析和验证，因此适合逐行流式生效。

文本数据使用精确的 `SEARCH/REPLACE`，避免重新输出整段长文本：

```text
PATCH #title_7
<<<<<<< SEARCH
Opening title
=======
Final title
>>>>>>> REPLACE
```

#### POST：在语义父节点下创建子树

```text
POST #track_9
before: #clip_12
<VideoClip source="assets/demo.mp4"
           start="0"
           duration="5000000" />
```

创建载荷直接使用领域原生 VML，而不是把一个节点拆成多次 `set_type`、`set_source`、`set_start` 和 `set_duration` 工具调用。XML 元素开始标签闭合后，解析器已经拥有节点类型与属性，可以经过模式投影后创建节点；后续子树继续在同一流中建立。

#### PUT：移动或重排已有节点

```text
PUT #clip_42
to: #track_10
before: #clip_13
```

移动保留节点身份。它与“删除旧节点再创建新节点”不同，因为引用和运行态身份不应因位置变化而丢失。

#### DELETE：删除节点及其语义子树

```text
DELETE #effect_3
```

删除必须经过领域规则验证，例如不能删除文档根，不能使必需结构失效，也不能留下不允许的引用。

### 3.4 有序、非原子脚本

一个编辑调用可以包含多个操作，按出现顺序执行：

```text
PATCH #clip_42
opacity="0.8"

PUT #clip_42
before: #clip_12
```

当前语义是：先前已成功的操作不会因为后续操作失败而回滚。因此不能把一次调用描述成数据库式全有或全无事务。更准确的单位是：

- 每个已完成操作或属性行是一个经过验证的局部写；
- 整次调用共享一个流式解析生命周期；
- 整次调用在用户 Undo 语义上归并为一个捕获边界；
- 最终工具结果在提交输入完成后只产生一次。

这个区分需要在论文中明确，否则“原子操作”“事务”和“Undo 分组”会被错误地混为一谈。

## 4. 面向模型流式输出的语法

### 4.1 为什么行协议比深层 JSON 更自然

模型从左到右生成 token。一个深层 JSON 参数通常要等待引号、转义、数组、对象和外层括号闭合后，通用解析器才能确认完整结构。REST-Edit 把完成条件放在局部边界上：

- 完整 `PATCH #id` 行确定目标；
- 完整 `name="value"` 行确定一次属性写；
- 完整 `DELETE #id` 行确定一次删除；
- `PUT` 块结束确定移动；
- XML 元素的结构闭合确定一次创建子树。

这不是说 JSON 天生不能流式解析，而是说本协议把可提交边界设计成了生成模型容易稳定产生的文本边界。

### 4.2 路径先于正文

工具输入保持一个非常小的外层结构：

```json
{
  "path": "compositions/main.vml",
  "changes": "PATCH #clip_42\nopacity=\"0.8\""
}
```

`path` 必须先输出，使客户端在 `changes` 尚未生成完时就能选择正确文档处理器。随后 JSON 字符串解码器把 `changes` 中已解码的文本连续送入领域解析器。外层 JSON 用于工具参数兼容，内层脚本才是面向编辑的协议。

### 4.3 渐进解析不绕过领域模型

实时解析出的操作不会直接修改随意的 JSON 字段，而是进入和最终提交调用相同的 `IFileCall`，再经过文档的投影编辑边界：

```text
model delta
  -> JSON string decoder
  -> REST-Edit line/XML parser
  -> schema projection and validation
  -> canonical document operation
  -> Y.Doc
```

因此，流式只是更早地交付同一语义，并没有建立第二套写路径。

## 5. 实时前缀与提交围栏

实时传输通常是低延迟但可能丢失的发布订阅通道；提交消息则是可持久化、可重放的权威记录。REST-Edit 把二者组合成同一次调用。

### 5.1 连续前缀规则

服务端为每个 `tool-input-delta` 标注原始输入偏移。客户端只在：

```text
delta.offset == expectedOffset
```

时消费该片段，并更新 `expectedOffset`。若页面重连后丢失中间片段，后续 delta 的偏移会出现缺口。客户端此时：

1. 保留已经通过验证并应用的连续前缀；
2. 停止消费当前调用的后续实时片段；
3. 等待最终提交输入；
4. 用同一个 `IFileCall` 补齐前缀之后的缺失后缀。

它不猜测缺失内容，也不重放已经执行的前缀。

### 5.2 提交输入是权威收口，不是第二次执行

假设实时通道已经应用长度为 (p) 的连续原始输入前缀，最终提交正文为 (F)：

- 若 (p=0)，完整应用 (F)；
- 若已消费文本是 (F) 的前缀，只送入尚未消费的后缀；
- 若实时文本与提交文本不满足前缀关系，调用失败；
- 最终解析器 `flush/end` 后才生成权威工具结果。

这一机制同时解决两类错误：

- 把实时前缀和提交输入各执行一次造成重复修改；
- 断线后从错误字节位置继续解析造成错位修改。

### 5.3 Undo 与执行结果

一个文档编辑调用从开始流式写入到提交或取消期间，共享一个 Undo 捕获区间。即使多个属性在不同 delta 到达，它们也可以由用户一次撤销。这里的“一次 Undo”不代表操作本身全有或全无；失败前已经成功的操作仍可能存在，但可以通过同一 Undo 步撤回。

> **[待补 R-C1：取消语义]** 当前取消会关闭捕获并清理“本次新建且未完成”的文件，但不会普遍逆转既有文档中已经流式生效的合法前缀。论文必须通过用户研究或故障实验判断是否需要显式 preview/commit 模式；不能把 cancel 描述成 rollback。

## 6. 与相关方法的关系

### 6.1 JSON Patch

[RFC 6902](https://www.rfc-editor.org/rfc/rfc6902) 定义了对 JSON 文档执行 `add`、`remove`、`replace`、`move`、`copy` 和 `test` 的操作数组。它是成熟的通用标准，也完全可以被系统用于协同、事务或 Undo；这些能力取决于宿主系统，不能被错误地写成 REST-Edit 的独占优势。

REST-Edit 与 JSON Patch 的关系是“解决相邻问题的不同表示选择”，不是继承关系：

| 维度 | JSON Patch | REST-Edit |
|---|---|---|
| 目标 | 通用 JSON 文档差分 | 已建模创作工程的语义节点编辑 |
| 定位 | JSON Pointer 路径 | 文件内稳定短 ID |
| 创建载荷 | JSON value | 原生领域 VML 子树 |
| 流式边界 | 通常以完整操作对象为边界 | 行、属性和 XML 结构边界 |
| 验证 | 通用 JSON 操作 + 宿主规则 | 每次操作直接投影到领域模式 |
| 重排 | 路径 move | 保持节点身份的语义父节点/兄弟定位 |

这张表只说明本文的设计取向，不能代替实证比较。

### 6.2 结构化时间线补丁

RefineCut 提出了面向视频时间线的类型化结构补丁和确定性验证器，是本文最重要的相邻工作之一。即使我们的设计是独立形成，也应当如实引用，因为学术引用说明的是知识图谱中的关系，不是声称实现来源。我们的可区分问题可以放在：语言模型的逐 token 流式协议、短语义地址、原生 VML 创建载荷、实时前缀与提交围栏，以及同一执行路径的渐进修改。

> **[待补 R-L1：RefineCut 精读]** 获取可引用全文，逐项核对其 patch schema、验证时机、事务语义、评测数据与是否支持渐进执行，避免只依据摘要比较。

### 6.3 多工具调用

另一种接口为每个动作提供独立函数，例如 `create_clip`、`set_clip_start`、`set_clip_duration`、`move_clip`。它的优点是每个工具具有明确参数模式，适合较少且稳定的动作集合；缺点是领域扩大后工具数量、选择负担和多轮调用开销会增长。

REST-Edit 的假设是：当节点模式已经负责验证时，可以用少数通用编辑操作承载大量领域节点，而无需为每个节点属性新增工具。这个优势必须在受控实验中证明，不能只做理论推断。

### 6.4 面向 Agent 的计算机接口

[SWE-agent](https://arxiv.org/abs/2405.15793) 表明，为语言模型专门设计的 Agent-Computer Interface 会显著影响其导航与代码编辑表现。REST-Edit 把这一观点延伸到结构化视频工程：AI 不必模仿鼠标点击，也不必重写整个序列化状态，而应获得符合其生成方式的语义编辑界面。

## 7. 贡献与创新性评估

建议论文把贡献控制在以下四点：

1. **语义局部表示**：以短稳定节点 ID 和有限资源操作表达对已建模创作工程的局部意图；
2. **生成友好语法**：把可判定边界设计为行、属性与 XML 结构闭合，使协议适合逐 token 输出；
3. **双通道收敛机制**：用带偏移的实时连续前缀获得低延迟，用提交输入作为权威围栏补齐并防重放；
4. **单路径执行**：实时与提交输入共享 `IFileCall`、领域验证、Y.Doc 写路径和 Undo 捕获，而不是维护两套编辑器。

创新强度应实事求是地定位为：**协议表示与流式执行机制的系统性优化**。它不需要宣称发明了 PATCH、语义 ID、增量编辑、CRDT 或 Undo。只要实验能证明这组设计在目标场景中带来更低成本、更低延迟或更高可靠性，就是可发表的工程与系统贡献。

## 8. 实验设计

### 8.1 任务集

至少覆盖：

- 单属性修改；
- 同节点多属性修改；
- 添加单节点与嵌套子树；
- 跨轨道移动和同轨重排；
- 精确删除；
- 文本替换；
- 包含错误 ID、非法属性、引用约束和中途断流的负向任务；
- 用户和 AI 同时修改不同节点或同一节点的协同任务；
- 长工程中的连续多步编辑。

> **[待补 R-D2：基准集]** 保存自然语言指令、初始工程、预期语义 diff、允许的等价结果及失败判定器。训练示例和测试任务必须隔离。

### 8.2 对照组

1. 完整 VML/JSON 重写；
2. JSON Patch；
3. 多个领域函数工具；
4. REST-Edit 但只在完整输入后执行；
5. REST-Edit 实时前缀 + 提交围栏；
6. REST-Edit 去掉短 ID、改用长路径的消融组。

### 8.3 指标

- 最终语义正确率；
- 首次通过验证的局部修改延迟；
- 最终完成延迟；
- 模型输入与输出 token；
- 线路传输字节；
- 工具调用次数与模型轮数；
- 被触及节点数、无关节点变化数；
- 模式验证失败率；
- 断流恢复正确率、重复执行率；
- 协同情况下保留的非冲突修改比例；
- 单次用户意图的 Undo 步数；
- 解析器 CPU 时间与客户端主线程阻塞。

### 8.4 需要提前埋点的数据

> **[待补 R-T1]** 每个 tool call 记录模型开始、首个 delta、path 完成、首个有效 operation、提交输入、最终结果六个时间点。

> **[待补 R-T2]** 记录原始输入 offset、缺口位置、已应用前缀长度、提交补齐长度、前缀不一致失败。

> **[待补 R-T3]** 记录每次操作的 target ID、operation kind、验证结果与写集合大小，但需要脱敏内容。

> **[待补 R-T4]** 同时保存局部脚本 token 与等价完整文档 token；没有后者就无法可信地报告节省比例。

> **[待补 R-T5]** 为多工具基线记录选择错误、调用次数、模型回合数和中间读取次数。

> **[待补 R-T6]** 将网络断流、重复 delta、乱序/缺口、页面重连做成可重复故障注入，而不是只统计线上偶发事故。

## 9. 威胁与限制

1. 稳定 ID 需要先通过读取或上下文暴露给模型，可能增加输入 token；
2. 行协议对含换行、转义和复杂文本载荷需要严格语法；
3. 逐行生效意味着用户可能短暂看到尚未完成的中间状态；
4. 非原子操作需要清晰错误与 Undo 语义；
5. 结果可能依赖基础模型对 XML、ID 和编辑示例的熟悉程度；
6. 与 JSON Patch 的差异可能来自领域模式而非表面语法，需要消融实验分离；
7. 当前协议首先服务可信项目编辑，不自动解决授权、恶意输入与任意代码执行问题。

## 10. 中文技术文章母稿

### 让 AI 像改代码一样精确剪视频

很多“AI 剪视频”的第一版实现都很像：把整个时间线变成 JSON，交给模型，然后让它输出一份新的 JSON。这个办法做演示很快，但工程一旦变大就会遇到一个根本问题——用户只改一句话，AI 却要重新抄一遍整个工程。

如果 AI 漏掉一条轨道、改坏一个素材引用，或者在它思考期间另一位用户刚好做了修改，完整覆盖就会把局部要求放大成全局写入。

我们的做法是把视频工程当成已经建模完成的运行态。片段、轨道、特效都有稳定身份。AI 不需要描述“第三条轨道里第十二个片段”，只需要说：

```text
PATCH #clip_42
opacity="0.8"
```

要加一个片段，它可以把原生结构直接放到目标轨道下面：

```text
POST #main_track
<VideoClip source="assets/demo.mp4" duration="5000000" />
```

真正重要的不是借用了几个大家熟悉的操作词，而是这个表达能随着模型输出逐步被理解。属性行一完成，编辑器就能验证并显示修改；一个新节点的开始标签闭合，类型和主要属性就已经明确。

实时输出又不是绝对可靠的。网页重连可能漏掉中间一段。因此我们给每段输入标原始位置：连续就继续，出现缺口就停。最后持久化的完整工具调用到达后，只补上没有处理的后半段。这样既能快，又不会把实时输入和最终输入执行两遍。

这套机制和 JSON Patch 并不是同一种东西。JSON Patch 是很成熟的通用 JSON 差分标准；我们解决的是另一层问题：怎样让 AI 对一个已经有领域模型的创作工程，使用短、语义化、可渐进解析的表达。两者应该在论文里正面比较，也应该互相引用，而不是为了证明新颖性硬说别人做不到协同或 Undo。

一篇工程论文不必声称翻天覆地。把接口变得更适合模型，把首个可见结果做得更快，把无关覆盖变少，把断流后的重复执行消掉，只要这些改进可以被严格测量，它们就是值得公开的知识。
