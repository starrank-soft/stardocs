## 摘要

Coding Agent 的能力不只来自模型会生成代码，还来自代码仓库为 Agent 提供了可寻址的文件、可检索的文本、局部编辑接口、编译器、测试和可重复执行环境。相比之下，许多 AI 视频编辑系统把视频编辑器当作图形界面，通过坐标点击、截图理解或大量领域函数调用完成操作。它们容易受到界面状态、可见区域、工具选择和长链路错误传播的影响。

本文提出 Edit-as-Code，一种面向视频创作 Agent 的计算机接口。它把视频项目投影为可导航的工程空间：时间线和文档以结构化 VML 文件表达，素材与生成结果以稳定 Artifact 路径和 ID 表达，Agent 使用 `glob`、`grep`、`read` 和 `head` 获取局部上下文，使用 `write` 与 REST-Edit 修改工程，并通过模式验证、引用检查、可视预览和程序化判定器闭环验证。耗时的媒体生成和转写任务保留为异步 Task，而不是伪装成文件编辑。

Edit-as-Code 的核心不是“用代码生成视频”，也不是把专业编辑器退化为命令行，而是让人类界面、Agent 接口和运行时共享同一个工程模型。人类仍可直接拖动时间线，Agent 也可通过语义文件接口工作；两者最终修改同一权威状态。本文计划通过真实后期制作任务，对比 GUI 操作、多领域工具编排、完整工程重写和 Edit-as-Code，评估成功率、工具步数、上下文成本、无关修改、恢复能力与用户可接管性。

## 1. 从“会写代码”重新理解“会剪视频”

软件工程 Agent 的工作环境具有几项容易被忽略的优势：

- 文件有稳定路径；
- 文本可以按范围读取和检索；
- 修改通常是局部差分；
- 编译器和类型系统能快速拒绝错误；
- 测试提供可重复的完成判据；
- 仓库本身承担外部记忆；
- 人类可以直接审查 diff 并继续修改。

因此，“像 Coding 一样剪辑”不意味着让模型输出一段 FFmpeg 命令或生成一个新的视频程序，而是把上述可工作性迁移到视频工程。

本文提出四个研究问题：

1. 视频项目能否形成 Agent 可读、可寻址、可局部修改的工程表示？
2. 同一表示能否同时服务人类编辑器、Agent 和协同运行态？
3. 类型验证、引用验证和视觉验证如何组成视频编辑的“编译与测试”闭环？
4. 与 GUI 点击和大量领域工具相比，这种 ACI 是否能减少步骤、上下文和不可恢复错误？

## 2. 设计原则

### 2.1 项目是外部记忆，不是一次性 Prompt

模型不应在每一轮上下文中携带完整时间线。项目文件保留权威结构，Agent 根据任务先定位再读取：

```text
glob("compositions/*.vml")
grep("assets/product", "compositions/*.vml")
read("compositions/main.vml#clip_42")
```

读取范围与当前决策相关，而不是与项目总大小绑定。

### 2.2 语义寻址优先于像素寻址

画布上的坐标属于视图状态：缩放、平移、窗口大小或布局变化都会改变像素位置。`compositions/main.vml#clip_42` 则指向工程语义。Agent 可以要求“移动这个 Clip 到另一个 Track”，编辑器再决定如何显示，而不是让 Agent 猜测拖拽起点和终点。

### 2.3 单一权威模型

Agent 不能维护一份“AI 时间线”，人类界面再维护另一份“真实时间线”。正确的数据流是：

```text
Human UI event ─┐
                ├─> Project model / Y.Doc ─> runtime projection ─> preview
Agent file edit ┘
```

两种入口共享领域操作、模式验证、引用约束、协同状态和 Undo。这样，人类可以在 Agent 工作前后继续编辑，不需要导入、导出或同步两份工程。

### 2.4 生成与编辑分层

“把现有片段移动两秒”和“生成一段新视频”不是同一种操作：

- 编辑是低延迟、确定性的工程状态修改；
- 生成是耗时、可能失败、需要模型和计费信息的异步任务；
- 生成结果先成为 Artifact，再被时间线引用；
- Agent 可以等待、监控或稍后接收 Task 结果。

把两者混成一个巨大工具会模糊故障、重试和权限边界。

## 3. 工程空间

### 3.1 可编辑文件

项目向 Agent 暴露几类文件：

| 类型 | 作用 | 典型编辑方式 |
|---|---|---|
| `.vml` | Composition、Track、Clip、Effect 等运行态文档 | REST-Edit |
| `.md` | 脚本、说明和文本资产 | 精确 SEARCH/REPLACE |
| `.svg` | 可编辑矢量图形 Artifact | 完整创建或源代码局部编辑 |
| `.mg` | 可编辑 Motion Graphic Artifact | 完整创建或源代码局部编辑 |
| 二进制媒体 | 视频、音频、图片等 Artifact | 读取元数据、引用，不直接文本改写 |

文件系统在这里是 Agent 视图，不要求底层真的把每个对象保存为普通磁盘文件。路径负责可发现性，稳定 ID 负责运行态引用，底层仍可使用数据库、对象存储和 Y.Doc。

### 3.2 结构化 VML

一个简化的时间线可以被投影为：

```xml
<Composition id="comp_main" width="1920" height="1080" fps="30">
  <VideoTrack id="track_main" name="Main">
    <VideoClip id="clip_42"
               source="assets/demo.mp4"
               start="0"
               duration="5000000" />
  </VideoTrack>
</Composition>
```

VML 既不是渲染器内部对象的无约束 dump，也不是要求模型手工管理的数据库。它是经过模式投影的公共语义表面：只暴露 Agent 能正确理解和修改的概念。

### 3.3 导航工具

Edit-as-Code 刻意复用 Coding Agent 熟悉的窄工具类别：

- `glob`：发现候选文件；
- `grep`：按路径、引用或文本定位对象；
- `read`：读取文件或锚定节点；
- `head`：读取大型素材或文档的有限元数据；
- `write`：创建完整源文件；
- `edit`：局部修改已有文件。

它们的数量保持稳定，领域能力主要由项目模式扩展，而不是每增加一种 Clip 或 Effect 就新增一个顶层工具。

## 4. 编辑闭环

### 4.1 Locate：定位

Agent 先把自然语言中的对象映射到项目实体。例如“把产品镜头后面的字幕改成最终标题”可能需要：

1. 搜索引用产品素材的 Clip；
2. 读取其附近的时间线结构；
3. 找到时间相邻或语义关联的 TextClip；
4. 获取稳定节点 ID。

定位结果应该尽可能小，但必须包含验证后续修改所需的上下文。

### 4.2 Plan：计划

模型把目标拆为可验证步骤。例如：先更新字幕，再移动片段，最后读取受影响范围。对简单操作不应强制生成冗长计划；对长链路任务则可把生成、转写、选材和时间线编辑分开。

### 4.3 Patch：修改

Agent 使用上一稿定义的 REST-Edit 做语义局部修改：

```text
PATCH #title_7
<<<<<<< SEARCH
Opening title
=======
Final title
>>>>>>> REPLACE
```

REST-Edit 是 Edit-as-Code 的一个实现组件。本文关注完整 ACI 与工作闭环；REST-Edit 论文关注协议表示和流式执行，两篇稿件需要用不同实验和贡献声明避免重复。

### 4.4 Verify：验证

视频编辑没有一个等同于单元测试的万能判定器，因此需要分层验证：

1. **语法验证**：编辑脚本和 VML 能否解析；
2. **模式验证**：节点类型、属性、父子关系是否合法；
3. **引用验证**：素材、文档和跨节点引用是否存在且兼容；
4. **结构断言**：目标节点是否具备预期属性、时间范围或父节点；
5. **媒体断言**：时长、帧率、声道、字幕时间是否满足要求；
6. **视觉验证**：抽取关键帧、缩略图或预览，让多模态模型或人类确认；
7. **用户验收**：审美性目标仍需人类判断。

程序化判定器应覆盖确定性事实，视觉判定负责它无法表达的构图和审美。不能用一次截图“看起来没问题”代替结构验证。

## 5. 为什么不是 GUI Agent

GUI 是为人的视觉和手部操作设计的。它擅长快速探索、直接操纵和审美判断，但对 Agent 存在额外的不稳定因素：

- 屏幕只显示工程的一小部分；
- 相同节点会因滚动、缩放和布局改变位置；
- 拖拽是否命中、吸附到哪里需要视觉反馈；
- 弹窗、焦点和动画会改变动作含义；
- 批量操作需要大量机械步骤。

这不意味着 GUI 没有价值。合理分工是：

- Agent 用语义接口执行精确、批量、可重复操作；
- 人类用 GUI 浏览、审美判断和直接修整；
- 多模态观察用于验证结果或处理确实只有视觉表面的内容；
- 两者共享同一个项目状态。

[OSWorld](https://arxiv.org/abs/2404.07972) 的分析显示，GUI grounding 仍容易在点击、选择和滚动等细节中失败，而可由代码解决的任务有时对 Agent 更直接。本文不把这一观察当作视频领域结论，而把它作为设计假设，在后期制作任务上重新验证。

## 6. 为什么不是“一个动作一个工具”

领域工具具有强类型和清晰名称，适合高价值、边界稳定的能力，例如 `transcribe` 或 `generate_video`。但若把每种结构修改都拆成工具，系统可能出现：

```text
create_video_track
create_video_clip
set_clip_source
set_clip_start
set_clip_duration
set_clip_crop
move_clip
...
```

工具描述会占用上下文，模型需要先选择工具再填参数，复合节点需要多次调用，模式的每次扩展都可能扩大顶层工具面。

Edit-as-Code 的取舍是：

- 对异步能力、外部系统和非文件资源保留专用工具；
- 对已经进入工程模型的结构编辑，使用稳定的文件导航与编辑接口；
- 由领域模式而不是工具数量承担扩展。

这仍是待验证的假设。VideoAgent 采用三十多个专用编辑 Agent 并报告了较高编排成功率，说明多工具/多 Agent 路线可以有效。我们的论文应把它作为有力基线，而不是先验判定其错误。

## 7. 与相关工作的关系

### 7.1 Agent 辅助视频编辑

[LAVE](https://arxiv.org/abs/2402.10294) 结合素材语言描述、LLM 规划、Agent 操作和直接 UI 编辑，强调人机共同创作，是本文在人机交互层面的重要参考。Edit-as-Code 更集中于 Agent-Computer Interface、项目表示、局部修改和验证闭环。

[VideoAgent](https://arxiv.org/abs/2606.23327) 通过三十多个专用编辑 Agent、意图过滤和图优化覆盖视频理解与编辑，并报告编排成功率与 API 成本结果。它代表多 Agent、多工具路线；本文代表稳定工程接口与少量通用编辑工具路线。

[AgenticVBench](https://arxiv.org/abs/2605.27705) 提供真实后期制作任务和程序化判定器/专家量表，并观察到 harness 会显著影响 Agent 行为。它为本文“接口本身决定能力上限”的假设提供了直接评测背景，也可以作为任务设计参考。

### 7.2 Agent-Computer Interface

[SWE-agent](https://arxiv.org/abs/2405.15793) 系统研究了为语言模型设计计算机接口对软件工程表现的影响。Edit-as-Code 的贡献不是重复 SWE-agent，而是将 ACI 问题带到一个具有连续时间、多媒体引用、视觉验收和协同运行态的创作领域。

### 7.3 代码式视频生成

Remotion、FFmpeg 脚本、Blender 脚本及其他代码生成方案可以用程序产生视频，具有可重复和可组合优势。Edit-as-Code 与它们的区别是：

- 目标是持续编辑一个可由人类 GUI 接管的工程；
- 时间线对象具有稳定身份与协同状态；
- Agent 修改的是公共项目语义，而非绕过编辑器另建渲染程序；
- 最终运行时仍负责交互预览、解码和导出。

> **[待补 E-L1：代码式视频系统综述]** 系统比较 Remotion、FFmpeg/MLT、Blender scripting、Lottie/动画代码生成和 NLE 插件脚本接口，避免把“代码生成视频”描述成空白领域。

## 8. 贡献与创新性评估

建议把贡献写成：

1. 一种把视频项目投影为文件、稳定 ID、结构化 DSL 和 Artifact 的 Agent 工程空间；
2. 一种将 Coding Agent 的 locate–patch–verify 工作方式迁移到连续时间创作工程的 ACI；
3. 一种让人类 GUI 与 Agent 文件接口共享同一权威运行态的协作架构；
4. 一套覆盖结构、引用、媒体和视觉结果的分层验证方法；
5. 一项对 GUI、多工具、完整重写和 Edit-as-Code 的后期制作任务实证研究。

本文更像系统与 HCI 论文，而不是基础模型算法论文。新意来自一组接口与工程抽象如何共同改变 Agent 的可用性。若没有对照实验，文章仍可作为高质量工程经验；若完成任务集、基线和用户研究，则更有论文价值。

## 9. 实验设计

### 9.1 任务集

建议从真实工作流选取 60–120 个任务，分为：

- 定位与微调：修改文本、音量、不透明度、起止时间；
- 结构操作：新增、删除、移动、重排 Clip/Track/Effect；
- 素材工作：导入、检索、替换引用；
- 多步编辑：转写、字幕、B-roll 插入、配乐与混音；
- 视觉任务：构图、标题位置、MG 调整；
- 长工程任务：跨文件检索与多个局部修改；
- 协同任务：人类在 Agent 运行期间修改另一部分工程；
- 恢复任务：工具失败、断线、生成 Task 延迟或返回失败。

> **[待补 E-D1：真实任务来源]** 记录任务由多少位剪辑师提供、经验年限、任务频率与敏感信息脱敏方式。

### 9.2 基线

1. 纯 GUI 多模态 Agent；
2. 一个动作一个领域工具的 Agent；
3. 完整项目重写 Agent；
4. Edit-as-Code，无视觉验证；
5. Edit-as-Code，完整分层验证；
6. 人类新手和专业剪辑师参考上限。

### 9.3 指标

- 任务成功率与部分成功率；
- 程序化判定器通过率和专家评分；
- 模型轮次、工具调用数、无效动作数；
- 输入/输出 token 和 API 成本；
- 完成时间、首个有效修改时间；
- 无关节点修改数；
- 错误后继续完成率；
- 人工接管后修复时间；
- 人类对可理解性、可预测性和控制感的评分。

### 9.4 消融

- 去掉稳定 ID，只允许层级路径；
- 去掉 grep/锚点读取，每次给完整文件；
- 去掉模式验证；
- 去掉视觉验证；
- 把通用 edit 拆成大量领域工具；
- Agent 与人类使用不同状态副本；
- 禁止 Agent 在修改后读取结果。

## 10. 研发阶段必须补的数据

> **[待补 E-T1]** 每轮记录 Agent 实际读取了哪些文件、节点与字节，建立“项目总量—读取量—任务规模”关系。

> **[待补 E-T2]** 对每次修改保存语义 diff、无关 diff、验证错误与最终是否被 Undo/人工修正。

> **[待补 E-T3]** 记录工具定义占用 prompt token，特别是多工具基线与稳定通用工具的差异。

> **[待补 E-T4]** 记录 locate、plan、patch、verify 四阶段耗时和失败点。

> **[待补 E-T5]** 建立截图/关键帧与结构状态配对数据，后续才能研究视觉验证是否真的提升成功率。

> **[待补 E-T6]** 收集人类在 Agent 结果上继续编辑的时间与步骤；“可接管”是本范式的重要价值，不能只测一次性自动完成。

## 11. 中文技术文章母稿

### 为什么 AI 会写代码，却还不太会剪视频

AI 写代码时拥有一个非常好的工作台。它可以搜索仓库、打开一个文件、只改三行、运行测试，然后根据错误继续。代码仓库替它记住了一切，编译器会告诉它哪里不合法，人类也能一眼看到它改了什么。

很多视频编辑 Agent 的工作台却完全不同。它看到一张截图，猜一个按钮，点击，等待界面变化，再猜下一步。或者它面对几十个细粒度工具，为“创建一个片段”连续调用创建、设置素材、设置时间和移动等函数。

问题未必只是模型不会剪辑，也可能是我们给它的接口不适合它。

如果把视频项目变成一个可读的工程，情况就会变化。时间线有文件路径，片段有稳定 ID，素材有可引用的 Artifact。AI 可以像查代码一样先搜索：产品镜头在哪里？它后面有哪些字幕？然后只改目标节点。编辑器的类型系统负责拒绝非法轨道关系，引用检查负责确认素材存在，最后再抽几张关键帧确认视觉效果。

这不是让所有剪辑师去写 XML。人类仍然使用时间线、预览和拖拽；AI 使用更适合机器的语义接口。两种操作进入同一个项目模型，所以人可以随时接过来继续修，而不必在“AI 工程”和“真实工程”之间来回导入。

我们把这种思路叫 Edit-as-Code。它并不表示视频就是代码，而是说，一个真正可工作的 Agent 环境应该像成熟的软件工程环境一样：状态可寻址，修改可局部化，错误可验证，过程可恢复，结果可由人继续接手。

## 12. 风险与边界

1. VML 投影若过于底层，会把实现细节泄露给模型；过于高层又可能丢失精确性；
2. 稳定 ID 与文件锚点会占用上下文，需要测量净收益；
3. 视觉质量无法完全由类型系统判断；
4. Agent 可编辑源文件会带来权限和代码安全问题，特别是 `.mg`；
5. 工程表示可能让模型偏向其训练中熟悉的 XML/代码模式，跨模型结果需要复现；
6. 专业软件的 GUI 具有很多高层语义动作，语义接口与 GUI 不是简单二选一；
7. 论文应报告失败案例，包括合法但审美错误的结果。
