# 单时钟可寻址 Motion Graphics：面向浏览器视频编辑的确定性可执行 SVG 运行时

> 中文论文母稿 + 中文技术文章母稿
>
> 论文英文候选标题：*Single-Clock Motion Graphics: A Deterministic and Random-Access Executable SVG Runtime for Browser Video Editors*
>
> 面向公众的文章标题：**《让同一份 MG 同时服务实时预览、缩略图和最终导出》**
>
> 状态：架构稿。本文的重点不是发明矢量动画，而是统一时间、执行与像素语义。

## 摘要

浏览器视频编辑器中的 Motion Graphics（MG）需要同时满足相互牵制的要求：创作者希望使用可编程动画表达复杂视觉逻辑，编辑器需要在任意时间点低延迟预览，缩略图和导出又必须得到与预览一致的像素。常见方案要么将动画预渲染为视频并失去可编辑性，要么分别实现 DOM 预览与离屏导出而产生语义漂移，要么依赖动画自身的墙钟和定时器，使 seek、scrub 和逐帧导出无法确定性复现。

本文提出一种单时钟、可随机访问的可执行 SVG Motion Graphics 运行时。每个 `.mg` 资源是一个自包含模块，包含可静态读取的元数据、一个封装单个 SVG 的组件，以及由编辑器显式调用的同步 `render(time)`。MG 不拥有播放循环，所有状态只由视频编辑器的时间输入驱动；任意时间点的结果必须独立于此前调用顺序。实时预览直接显示该 SVG，缩略图、抽帧和导出则克隆同一组件的当前 SVG、序列化并栅格化到像素表面，从而共享动画实现而非维护第二套渲染器。

系统进一步以稳定 Artifact ID 和不可变内容哈希分离时间线引用与源代码版本，并以静态元数据投影驱动生成、导入、编辑和运行时加载。本文计划评估随机 seek 确定性、预览/导出像素一致性、首帧延迟、逐帧吞吐、内存、缓存复用和编辑响应，并与 Lottie、预渲染视频、iframe/独立页面捕获及预览/导出双实现方案比较。

## 1. 问题定义

一个 MG 片段至少有五类消费者：

1. 时间线实时预览；
2. 播放、seek 和 scrub；
3. 时间线缩略图或封面；
4. 单帧抽取和画面分析；
5. 最终逐帧导出。

如果每个消费者建立自己的动画时钟和渲染路径，同一时间点可能出现不同结果。例如预览使用浏览器 DOM，缩略图使用截图服务，导出使用另一套服务器渲染器；字体、时间推进、随机数、资源加载和动画库版本的差异都会累积成像素漂移。

本文研究三个核心问题：

1. 怎样让可编程动画支持任意顺序、任意时间点的确定性求值？
2. 怎样让 DOM/SVG 的低延迟预览与 Canvas/编码器需要的像素共享同一语义？
3. 怎样在保持源文件可编辑的同时，为运行时加载、缓存和版本切换提供稳定身份？

## 2. 设计目标与非目标

### 2.1 设计目标

- **单一时间源**：编辑器是唯一时钟；
- **随机访问**：`render(t)` 不依赖 `render(t-Δ)`；
- **同源渲染**：预览与像素消费者使用同一组件实例与 SVG 状态；
- **可静态发现**：无需执行任意代码即可读取关键元数据；
- **可编辑版本**：时间线引用稳定，源内容按哈希不可变；
- **浏览器原生**：利用 DOM、SVG、Shadow DOM、Canvas 和 ImageBitmap；
- **组合友好**：MG 作为普通视觉 Clip 与视频、图片、文本共同参与 Composition。

### 2.2 非目标

- 不定义完整通用动画交换标准；
- 不取代 Lottie、Rive 或 Web Animations；
- 不在当前可信项目模型下解决任意第三方 JavaScript 的强隔离；
- 不保证所有 SVG 特性、外部字体和浏览器实现跨平台逐像素完全一致；
- 不要求服务器拥有一套独立的 MG 解释器。

## 3. `.mg` 资源契约

### 3.1 自包含模块

一个 MG 源文件包含三项公共契约：

```js
export const metadata = {
  width: 1920,
  height: 1080,
  duration: 5,
  variables: {
    title: { type: "string", default: "Launch" }
  }
};

export default class LaunchTitle extends HTMLElement {
  // mount exactly one SVG inside a shadow root
  // receive props from the host
  // render(time) reconstructs the exact visual state
}
```

具体 API 可以继续迭代，但论文必须固定以下不变量：

- `metadata` 是可静态读取的字面量；
- 默认导出是可实例化的组件；
- 组件拥有一个 Shadow Root，并以一个 SVG 为视觉根；
- `render(time)` 同步更新该 SVG；
- 宿主而非组件驱动时间；
- 可变参数通过明确 props/variables 进入，不从全局 UI 状态偷取。

### 3.2 为什么元数据必须静态可读

若获取宽高、时长或变量模式需要执行整个模块，资源发现、导入和列表展示都会变成代码执行。静态元数据允许系统在不实例化动画的情况下完成：

- 文件校验；
- 资源卡片展示；
- 时间线默认时长；
- 参数面板生成；
- 任务结果入库；
- 内容哈希与缓存规划。

元数据只能有一个权威字面量。若生成服务、数据库记录、运行时类和 UI 各自维护一份宽高与时长，版本漂移几乎不可避免。

> **[待补 M-C1：静态提取规范]** 固定允许的 JavaScript/TypeScript 子集、解析器、错误位置与 canonical serialization。必须明确是 AST 提取还是受限求值。

### 3.3 可执行 SVG 的取舍

SVG 提供矢量几何、文本、滤镜、遮罩和 DOM 可变性；JavaScript 组件提供程序化组合与变量；动画库可用于构建暂停的时间线。但可执行模块比纯声明式 JSON 更难移植和隔离。

因此本文不宣称这种格式优于所有声明式格式，而是针对“浏览器内专业编辑 + AI 可生成/修改 + 统一预览和导出”这一场景选择表达能力与系统一致性。

## 4. 单时钟模型

### 4.1 从全局时间到片段局部时间

设 Composition 时间为 (T)，Clip 在时间线上的起点为 (S)，播放速率为 (r)，源内偏移为 (O)，则 MG 接收的局部时间可以写为：

\[
t = O + (T - S)r
\]

裁剪、循环、反向和时间变换可以继续在宿主层计算，但组件最终只接收一个明确的局部时间 (t)。它不读取 `Date.now()`、`performance.now()` 或自己的 `requestAnimationFrame`。

### 4.2 `render(time)` 的随机访问不变量

对任意时间 (t) 和任意历史调用序列 (H)：

\[
Render(H, t) = Render(\varnothing, t)
\]

换句话说：先渲染 4 秒、再跳回 1 秒，必须与首次直接渲染 1 秒相同。播放顺序、帧率和设备性能不能改变最终状态。

[Web Animations](https://www.w3.org/TR/web-animations-1/) 的核心 timing model 同样强调由输入时间产生进度、与此前输入无关，因此具有帧率独立、方向无关和潜在常数时间 seek 等性质。本文借鉴这一时序原则，但将它落实为视频编辑器对可执行 SVG 组件的宿主契约。

### 4.3 允许和禁止的状态

允许：

- 构造时建立 DOM 与暂停的动画时间线；
- 缓存不改变语义的节点引用或插值表；
- 在 `render(t)` 中把受控动画时间线 seek 到 (t)；
- 使用由 `t` 和固定种子决定的伪随机函数。

禁止：

- 自己启动 `requestAnimationFrame`；
- 使用 `setTimeout`、墙钟或累计 `deltaTime` 驱动可见状态；
- 根据上一次渲染结果继续积分；
- 在随机 seek 时依赖未重建的粒子历史；
- 从不受版本控制的外部全局状态读取视觉参数。

如果需要粒子或物理效果，组件必须提供从固定种子与绝对时间重建状态的方法，或显式声明它不满足随机访问契约。

## 5. 同一组件服务实时预览与像素输出

### 5.1 实时预览路径

浏览器预览直接把 MG 组件放入 Composition 的 HTML/SVG 层：

```text
Composition clock
  -> clip local time
  -> component.render(time)
  -> live SVG in DOM
```

这一方式保留矢量清晰度、DOM 更新效率和即时参数编辑，不需要每帧把动画截图再贴回预览。

### 5.2 像素路径

缩略图、抽帧和导出需要 Canvas 或编码器可消费的像素：

```text
component.render(time)
  -> clone current SVG
  -> serialize SVG
  -> decode to ImageBitmap
  -> composite into Canvas
  -> thumbnail / frame / encoder
```

关键点不是“SVG 一定能完美栅格化”，而是像素路径读取**同一个组件在同一个时间点的当前 SVG**。没有另一套关键帧解释器，也没有服务器重新实现一次动画逻辑。

### 5.3 语义一致不等于绝对像素相同

预览 DOM 与导出 Canvas 可能因抗锯齿、色彩管理、字体加载和浏览器实现产生细小像素差异。因此论文应区分：

- **语义一致**：几何、文本、属性和动画进度来自同一组件状态；
- **像素近似一致**：像素差异低于设定阈值；
- **逐像素一致**：只有固定浏览器、字体、DPR、色彩空间和栅格化配置时才可能主张。

> **[待补 M-C2：渲染环境锁定]** 固定浏览器版本、字体包、设备像素比、色彩空间、SVG 外部资源策略和 Canvas 尺寸。

## 6. Artifact 身份与不可变内容

MG 源代码属于可编辑 Artifact，而不是直接嵌入协同文档的巨大字符串。时间线 Clip 保存稳定 Artifact ID；每次编辑产生一个新的不可变内容 Blob，并原子移动 Artifact 的当前内容哈希。

```text
Clip.source ─> stable Artifact ID ─> current content hash ─> immutable .mg source
```

这一分层带来：

- 时间线引用不因内容更新而改变；
- 运行时缓存可以按内容哈希复用；
- 旧内容可追踪、比较或回滚；
- 多个 Clip 可以引用同一 Artifact，并各自拥有变量 props；
- 内容变更后只失效相关哈希缓存。

运行时加载应保证同一内容哈希只创建一个模块加载 Promise，并为每个内容版本注册唯一自定义元素名称；每个 Clip 仍拥有独立组件实例，避免可见状态串扰。

## 7. 与其他方案的关系

### 7.1 Lottie

[Lottie 1.0](https://lottie.github.io/lottie-spec/1.0/single-page/) 是成熟的 JSON 矢量动画交换规范，拥有广泛工具和播放器生态。Lottie 的声明式数据、跨平台性和安全表面是明显优势。

本文方案的不同取舍是：

- `.mg` 是可执行组件，表达力更接近 Web/SVG 编程；
- 静态元数据与运行时代码共处一个资源；
- 组件必须暴露显式随机访问 `render(time)`；
- 预览和像素提取围绕同一 live SVG 组件设计；
- AI 可以像编辑源文件一样局部修改 `.mg`。

实验不能只比较文件大小或渲染速度，因为两种格式支持的效果集合不同。应选取两者都能表达的动画子集进行公平比较，并单独报告可执行 MG 的额外表达能力。

### 7.2 Web Animations、CSS Animation 与 SMIL

Web Animations 提供抽象 timing model 与浏览器 API，CSS/SMIL 提供声明式动画机制。它们可以成为 `.mg` 内部实现工具。本文的新增系统问题是：视频编辑器如何接管唯一时间、如何强制随机访问、如何把同一 SVG 状态交给缩略图和编码器，以及如何管理可编辑 Artifact 版本。

### 7.3 预渲染视频

预渲染视频易于播放和导出，也天然兼容现有解码管线，但会丢失参数级编辑、分辨率无关缩放和快速内容修改。它适合作为发布缓存或低能力设备降级，不适合作为唯一源表示。

### 7.4 iframe 或独立 Chromium 捕获

独立页面能隔离样式并运行任意 Web 动画，但会引入进程/文档生命周期、时钟同步、截图往返和资源加载差异。如果预览和导出分别运行两个页面，仍可能产生状态漂移。iframe 还不等于强安全沙箱，具体能力取决于 sandbox、CSP 和同源策略。

### 7.5 双渲染器

一种常见设计是 DOM 负责预览，服务器或 Worker 中的另一套解释器负责导出。它可能获得更高吞吐或跨平台能力，但需要长期维护两份语义。本文把“单实现一致性”置于首位，再通过缓存、ImageBitmap 和并行媒体解码优化性能。

## 8. 贡献与创新性评估

建议将论文贡献表述为：

1. 一个同时包含静态元数据和可执行 SVG 组件的可编辑 MG 资源契约；
2. 一个由视频编辑器唯一驱动、要求调用顺序无关的 `render(time)` 随机访问模型；
3. 一条让实时 DOM 预览与缩略图/抽帧/导出共享组件状态的同源渲染路径；
4. 一种稳定 Artifact 身份与不可变内容哈希结合的加载和版本模型；
5. 对确定性、一致性、交互延迟和逐帧性能的系统评测。

单独看“SVG 动画”“seek 动画”或“代码生成动画”都不是新问题。更可信的创新点是这五项约束在浏览器视频编辑场景中的组合，以及通过实验证明它减少了多渲染路径的语义漂移。

## 9. 实验设计

### 9.1 动画集合

至少包括：

- 文本淡入淡出与位移；
- 多层标题、lower third 和 callout；
- 遮罩、渐变、滤镜和路径动画；
- 参数化颜色、文字、数字和品牌主题；
- 重复、反向、速度变化；
- 固定种子粒子或程序化图表；
- 复杂 SVG 节点数量与不同持续时间。

> **[待补 M-D1：MG 语料]** 保存来源、复杂度、SVG 节点数、动画轨道数、滤镜数、字体、外部资源和对应 Lottie 可表达性标签。

### 9.2 基线

1. Lottie Web；
2. 同等视觉效果的预渲染透明视频；
3. 独立页面/iframe + 截图或帧捕获；
4. DOM 预览 + 独立导出解释器；
5. 本文方案，但允许组件自有墙钟；
6. 本文完整单时钟方案。

### 9.3 指标

- 首次实例化与首帧时间；
- 连续播放平均/尾部帧耗时；
- 随机 seek 延迟；
- scrub 时丢帧与主线程长任务；
- 1080p/4K 逐帧导出吞吐；
- DOM 节点、JS heap、GPU/位图内存；
- 内容哈希缓存命中；
- 随机顺序渲染与顺序渲染的状态差异；
- 预览截图与导出帧的像素差异；
- 参数修改到可见结果延迟；
- 同一项目重复导出的确定性哈希。

### 9.4 确定性测试

对每个动画采样时间集合 (T)，生成多种调用顺序：

- 单调递增；
- 单调递减；
- 随机排列；
- 带重复时间；
- 大跨度 seek；
- 不同播放帧率。

在每个 (t \in T) 比较 SVG canonical state 与像素结果。如果结果依赖调用顺序，记录具体节点和属性，而不是只给整体相似度。

### 9.5 需要提前埋点的数据

> **[待补 M-T1]** 每次模块解析、导入、实例化、`render(t)`、SVG 序列化、ImageBitmap 解码和 Canvas 合成分别计时。

> **[待补 M-T2]** 记录内容哈希、组件实例数、缓存复用和失效原因。

> **[待补 M-T3]** 对随机 seek 自动保存 canonical SVG hash 与像素感知 hash。

> **[待补 M-T4]** 记录字体 ready、外部图片 ready 与首次稳定帧，避免把资源未加载误判为时间不确定。

> **[待补 M-T5]** 记录预览、缩略图、抽帧、导出分别经过的代码路径，建立“同源率”检查，防止研发中悄悄出现第二实现。

## 10. 安全边界

当前 `.mg` 是可信项目代码。Shadow DOM 解决样式和 DOM 封装，不是 JavaScript 安全沙箱。一个可执行模块仍可能访问网络、占用主线程、读取可见全局对象或执行恶意代码。

如果未来允许公共市场上传任意 MG，必须单独设计：

- 代码签名与来源信任；
- CSP 与网络能力；
- Worker/iframe/进程隔离；
- CPU、内存与执行时间配额；
- 依赖白名单与构建产物审计；
- 外部资源和字体策略；
- 确定性 API 白名单。

论文不能把 Shadow DOM 写成安全贡献。可信项目运行时与公共第三方运行时应明确分开。

## 11. 中文技术文章母稿

### 让同一份 MG 同时服务实时预览、缩略图和最终导出

做视频编辑器里的 MG，最麻烦的不是让一个标题动起来，而是让它在所有地方都以同样的方式动。

预览里它可能是一个 SVG；时间线缩略图来自截图；导出又在服务器上跑另一套渲染器。三套路径刚开始看起来一样，几个月后就会出现字体不同、动画早一帧、滤镜不一致，甚至用户暂停的位置与导出帧完全不同。

我们的选择是只承认一个动画实现和一个时钟。

每个 `.mg` 文件是一个可执行 SVG 组件。它不自己播放，不读墙上的时间，也不开 `requestAnimationFrame`。编辑器告诉它现在是 1.37 秒，它就把整个 SVG 重建到 1.37 秒应该有的状态。无论之前渲染过 4 秒还是 0 秒，结果都应该一样。

实时预览直接显示这个 SVG，不需要不断截图。需要缩略图或导出时，系统先让同一个组件渲染到准确时间，再克隆它当前的 SVG，转成 ImageBitmap，合成到 Canvas。这样预览和导出不是“两套代码努力做得一样”，而是从一开始就读取同一份状态。

源文件仍然可以被修改。时间线引用的是稳定的 Artifact ID，内容每次更新产生新哈希。Clip 不用换引用，运行时却能准确知道哪些缓存应当失效。AI 也可以像编辑其他源文件一样改文字、颜色和动画逻辑。

这条路线不是为了否定 Lottie。Lottie 的声明式格式、跨平台播放器和生态非常成熟。可执行 MG 选择了另一种取舍：更接近 Web 编程的表达能力、更直接的 AI 源码编辑，以及浏览器编辑器内预览与导出的同源性。它的代价也很明确——代码安全、确定性约束和跨平台一致性都需要更严格的工程治理。
