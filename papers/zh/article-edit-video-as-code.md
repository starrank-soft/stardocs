# 为什么 AI 会写代码，却还不太会剪视频

> 面向公众的技术文章
>
> 方法名：Edit Video as Code
>
> 核心命题：不是让 AI 模拟人类点击剪辑软件，也不是让 AI 用代码重新生成一条视频，而是把已经建模的视频工程，变成一套 AI 可以像代码仓库一样发现、读取、局部修改和验证的工作界面。

今天的 AI 已经可以在大型代码仓库里完成相当复杂的工作。它会先看目录，搜索符号，打开相关文件，只改几行，再跑编译或测试，根据错误继续改。

这件事经常被概括成「模型会写代码了」。模型能力只是其中一半。另一半来自软件工程给 AI 提供的工作环境：文件有稳定路径，内容可以按需读取，修改可以是局部补丁，编译器和测试会拒绝错误，仓库本身替它记住一切，人类可以看 diff，随时接过来继续做。

反过来看视频剪辑，很多 AI 系统给模型的工作环境仍然很原始。一种路线是让它看截图、找按钮、模拟点击和拖拽。另一种是给它几十上百个细粒度工具：创建轨道、创建片段、设置素材、设置时长、设置位置。还有一种是把整条时间线序列化成一份大文档，让模型重新输出完整工程。

这些方案都能工作。但它们没有真正复用 AI Coding 已经证明有效的工作方式。

问题未必只是模型不会剪辑。也可能是我们给它的接口，本来就不适合它。

## 先说清楚：这不是用代码生成视频

FFmpeg 脚本、Remotion 页面或 Blender 脚本都可以生成视频。它们通常建立的是一套新的渲染程序。生成结果未必还是一个能被普通剪辑界面继续编辑的工程。

Edit Video as Code 要解决的是另一件事：

- AI 改的是用户当前打开的项目；
- 改完后，时间线、预览和属性面板看到同一结果；
- 用户可以继续拖动、调整和撤销；
- 人和 AI 不需要在两个工程之间导入、导出或同步。

所以，「像 Coding 一样剪辑」不是让模型输出一段 FFmpeg，也不是让所有剪辑师去写 XML。它是说：一个真正可工作的 Agent 环境，应该像成熟的软件工程环境一样——状态可寻址，修改可局部化，错误可验证，结果可由人继续接手。

## 视频项目怎样变成一份可工作的外部记忆

模型不该在每一轮上下文里携带完整时间线。项目文件保留权威结构，Agent 根据任务先定位，再读取。

一个视频项目可以对 AI 呈现成这样：

```text
assets/
  product-demo.mp4
  product-shot.png
docs/
  script.md
compositions/
  main.vml
```

这棵树是给 AI 用的工作视图，不是把内部存储逐项摊开，也不是复制一份临时目录再做双向同步。文件负责发现和读取；真正写入仍然回到原来的项目状态，并经过领域约束：这条轨道能否放这种片段，素材是否存在，时间关系是否合法。

它需要两种地址。文件路径负责发现：产品演示在哪个素材里，哪条时间线引用了它。稳定节点 ID 负责修改：找到之后，改的是 `compositions/main.vml#clip_product`，而不是「左边数第三条轨道的第 12 个片段」。数组下标是序列化布局，不是语义身份；前面插入一条轨道，整条路径的含义就会变。

于是一次真实任务可以很短。用户说：找到产品演示镜头，把它缩短到三秒，并在后面加一张产品海报。Agent 不必先看完整时间线。它可以搜索素材引用，读目标附近的结构，然后只改这一处：

```text
grep("assets/product-demo.mp4", "compositions/*.vml")
→ compositions/main.vml#clip_product

PATCH #clip_product
把时长改为 3 秒

POST 同一轨道
在它后面插入产品海报
```

读取范围跟当前任务有关，不跟项目总大小绑定。修改范围跟用户意图有关，不要求复述整条时间线。时间线可以对 AI 呈现为可读文本，但权威状态不是这段文本，所以不能靠全文替换来改结构。

AI 看到的是文件，改的仍然是专业编辑器里的同一份工程。

## 人机不是两套工程

这是整件事里最容易被忽略、也最值得被记住的一点。

如果 AI 维护一份「AI 时间线」，人类界面再维护另一份「真实时间线」，协作从一开始就断了。人要接管，就得导入、导出、对差异、重新理解一份自己没参与过的工程。

正确的数据流只有一份权威状态。人拖动时间线，和 Agent 提交一次局部修改，进入的是同一个项目模型。预览、撤销、协同都走原有通道。AI 不需要额外通知界面刷新；人也不需要在 Agent 结束后，再打开另一份旁路文件。

人类仍然使用时间线、预览和拖拽，去做探索和审美判断。AI 使用更适合机器的语义接口，去做精确定位、批量修改和可重复操作。两种入口共享同一份工程，所以人可以在 Agent 工作前后继续改，而不必先学会一套「AI 工程」。

AI 没有产出一个封闭的最终视频，而是在专业编辑工程中留下可见、可撤销、可继续修改的结构变化。

[SWE-agent](https://arxiv.org/abs/2405.15793) 的研究说明：给语言模型的计算机接口，会显著影响它完成软件工程任务的能力。视频编辑把同一个问题带到了连续时间、媒体引用、视觉验收和协同状态里。我们讨论的是这个接口问题，不是把软件工程工具直接搬进剪辑器。

## 现在能说什么，还不能说什么

这是一套接口设计，不是已经完成对照实验的结论。

我们还不能说它一定比 GUI Agent、多工具 Agent 或完整工程重写更成功。那些路线都可以有效；多工具、多 Agent 编排已经能做出结果。真正要比较的是：在真实后期制作任务里，哪种接口让步骤更少、上下文更省、错误更可恢复、人更好接手。这些评测仍在设计中。

有一件事现在就可以说清楚：视觉好不好看，类型系统判不了。程序可以拒绝非法轨道、断裂引用和错误时长；构图、节奏和审美仍然要看画面，也仍然需要人。

局部编辑如何写成短协议、如何随模型输出逐步执行，是下一层的问题。更完整的研究设计、对比实验和待补证据，见 [Edit-as-Code 论文母稿](./03-edit-as-code.md)；编辑协议见 [REST-Edit](./02-rest-edit.md)。

## 结语

视频工程不会因为 AI 的出现，就变成一堆普通文本。它仍然包含连续时间、媒体引用、渲染状态和专业约束。

但 AI 不应该被迫通过像素坐标理解这一切，也不应该每次重新输出完整工程。

当项目可发现、状态可寻址、修改可局部化、错误可验证、人类可接管时，AI 才不只是「会调用几个剪辑工具」。它才真正获得了像 Coding 一样、持续理解和修改视频工程的能力。
